## 1. Резюме

Система работает и работает корректно. На момент аудита: все 13 контейнеров `healthy`, `RestartCount=0` у всех, Kafka lag = 0 по всем пяти consumer-группам, за сутки в логах ровно одна запись уровня WARN (штатный реконнект Discord). Свежие recap-картинки — настоящие скриншоты (1.4–1.6 МБ), не fallback-заглушки. `go vet` чист по всем модулям.

Главная проблема не в багах, а в **несоответствии масштаба инфраструктуры масштабу задачи**.

Фактическая нагрузка за всю жизнь системы: 572 обработанных Discord-сообщения, 600 картинок, 49 недельных постов. Реальный профиль работы — батч раз в неделю: приходит пачка из ~12 игр, система обрабатывает её за 5–6 минут и простаивает до следующей недели.

Под эту задачу развёрнуто: Kafka + Zookeeper (**480 МБ RAM, 65% всего потребления стека**), MongoDB, дублирующая данные Postgres (66 МБ), 7 отдельных Go-контейнеров с 7 health-серверами и 7 пулами соединений (68 МБ суммарно). То есть транспорт сообщений потребляет в 7 раз больше памяти, чем вся бизнес-логика проекта.

При этом диск Pi занят на 72%, из них **13,6 ГБ Docker-образов подлежат немедленной очистке**, а температура — 75,9 °C при пороге троттлинга 80 °C.

Детально по снижению нагрузки — раздел 6. Экономия без потери функциональности: **~500–550 МБ RAM (65–70% стека) и ~14 ГБ диска**.

## 2. Что это и как работает

### 2.1 Назначение

Конвейер: Discord-канал лиги NeonSportz → Telegram. Две ветки:

- **week** — при смене игровой недели формируется текстовый пост со списком матчей и упоминаниями игроков;
- **game** — по завершении матча генерируется recap-картинка и отправляется в чат.

### 2.2 Поток данных

```
Discord Channel (gateway + REST)
        │  MessageCreate / backfill при reconnect
        ▼
discord-kafka-listener ──► topic: discord-message-ids  (value = message ID)
        │  buffered writer с retry-heap и exponential backoff
        ▼
discord-kafka-processor
        │  FetchMessage по REST, парсинг embeds регулярками
        ├──► topic: discord-week-updates  (JSON {season, week, title})
        └──► topic: discord-game-updates  (value = game ID)
                │                              │
                ▼                              ▼
   discord-kafka-week-formatter      discord-kafka-game-image
   (teams + schedule_games из PG)    (Chrome-скриншот → MinIO)
                │                              │
                ▼                              ▼
   topic: telegram-week-updates      topic: discord-game-images (JSON-событие)
                │                              │
                ▼                              ▼
   telegram-week-sender ─► TG        telegram-game-sender ─► TG
                                     (скачивает объект из MinIO, шлёт как photo)
```

### 2.3 Единый паттерн сервисов

Все шесть сервисов конвейера построены по одной схеме, и это сильная сторона проекта — читается предсказуемо:

1. `config.Load()` — вся конфигурация из env, ручные хелперы `requiredEnv`/`optionalEnv`/`durationEnv`/`intEnv`;
2. `waitFor*()` — блокирующее ожидание готовности Postgres/Mongo/MinIO с ретраями;
3. `EnsureSchema()` — автомиграция таблиц через `CREATE TABLE IF NOT EXISTS`;
4. health-сервер на `:8080/health`, проверяющий все downstream-зависимости;
5. `Processor.Run()` = `reprocessPending()` (добор недоделанного при старте) + `retryLoop()` (тикер) + `consumeLoop()` (Kafka);
6. graceful shutdown через `signal.NotifyContext`.

### 2.4 Модель надёжности

Kafka здесь — только транспорт «разбуди следующего». Настоящая гарантия доставки — **статусные таблицы в Postgres**, по одной на сервис:

| Таблица | Владелец |
|---|---|
| `discord_message_status` / `_failed` | processor |
| `week_message_status` / `_failed` | week-formatter |
| `game_image_status` / `_failed` | game-image |
| `telegram_week_status` / `_failed` | telegram-week-sender |
| `telegram_game_status` / `_failed` | telegram-game-sender |

Жизненный цикл: `new` → (`in_progress`) → `processed`, либо после `PROCESS_MAX_ATTEMPTS=10` попыток — перенос в `*_failed` и удаление из основной таблицы. Все вставки идемпотентны (`ON CONFLICT DO NOTHING`), offset коммитится сразу после записи в Postgres, а не после успешной обработки — то есть Kafka можно потерять целиком, конвейер восстановится из `reprocessPending`.

Это грамотное решение, и именно оно делает Kafka в текущем виде избыточной (см. 6.2).

### 2.5 Генерация картинок

Три реализации за интерфейсом `middle.Fetcher`:

| Режим | Механизм | Статус |
|---|---|---|
| `gochrome` | chromedp: загрузка страницы → клик по вкладке Recap → скрытие CMP-оверлеев → ожидание ассетов → инъекция фона стадиона → скриншот `.recap-wrapper` | **используется в проде** |
| `headless` | Нативная отрисовка через `fogleman/gg` по данным API | дефолт в коде, не используется |
| `selenium` | Remote WebDriver, клик по кнопке Download | профиль выключен, мёртвый код |

В `gochrome` есть двухуровневая деградация: при таймауте API или падении скриншота рисуется fallback-карточка (~100 КБ) из метаданных игры. Замер по Mongo: 11 игр за 6 минут (07:49–07:55), в среднем ~25–30 с на игру, один хвост в 2 мин 40 с.

## 4. Как написан код

### 4.1 Что сделано хорошо

- **Единообразие.** Шесть сервисов — один скелет. Новый сервис пишется копированием соседнего, и это здесь работает.
- **Идемпотентность продумана системно.** `ON CONFLICT DO NOTHING`, `$setOnInsert` в Mongo, `TouchAttempt` с проверкой eligibility, дедуп по `messageID:gameID`.
- **Устойчивость к рестартам.** `reprocessPending` при старте, отдельный `retryLoop`, `*_failed`-таблицы вместо тихой потери. Систему можно убить в любой момент — она доедет.
- **Buffered writer в listener** (`kafka/buffered_writer.go`) — аккуратная реализация: min-heap по времени следующей попытки, exponential backoff с jitter (20%), ограничение очереди, дедупликация pending. Для 220 строк это качественный код.
- **Работа с деградацией NeonSportz.** Двойные CSS-селекторы (`#recap-wrapper, .recap-wrapper`) после редизайна, `awaitPromise` для async-сниппетов, блокировка CMP-скриптов на уровне сети вместо кликов по баннерам, fallback-карточка. Видно, что каждый костыль — след реального инцидента, и они прокомментированы по делу.
- **Секреты не утекли.** `.env` действительно был закоммичен в четырёх коммитах (2024-12 … 2025-12), но проверка показала: там только плейсхолдеры `replace-me` и дефолтные `megagames`. Реальных токенов в истории нет.
- **`go vet` чист** по всем семи модулям.

### 4.2 Системные слабости

**Копипаста вместо общего модуля.** `config.go` каждого сервиса содержит одни и те же `requiredEnv`/`optionalEnv`/`durationEnv`/`intEnv`/`splitAndTrim` — пять функций × шесть сервисов. `sleepWithContext` продублирована шесть раз, `kafkaPing` — четыре, `kafkaDetails` — пять, `waitForPostgres` — пять, весь `startHealthServer` — пять. Это ~800 строк дублей. Из-за этого расходятся детали: `intEnv` в одних сервисах требует `> 0`, в других — `>= 0`; `TouchAttempt` в week-sender реализован иначе, чем в game-sender (и это уже вылилось в дефект P1-3).

**Ноль тестов.** Ни одного `*_test.go`. AGENTS.md фиксирует это как осознанное решение («healthcheck'и + статусные таблицы вместо тестов»), и для интеграционной части это защитимо. Но чистые функции без внешних зависимостей — `parser.ParseMessage`, `parser.parseWeek`, `formatter.BuildWeekMessage`, `headless.parseColor`, `headless.JSONInt.UnmarshalJSON`, `storage.ObjectKey` — тестируются за час и покрывают ровно те места, где сейчас сидят дефекты P1-1 и P1-2.

**Мёртвый код.** Пакет `selenium` целиком (профиль выключен), в нём же неиспользуемые `makeScreenshot` (пишет в несуществующий `/mega/screens/`) и `waitPage` (содержит `log.Fatal()` без `.Msg()` — не логирует и не завершает процесс, просто утечка zerolog-события). Пакет `headless` не используется в проде. `retryItem.index` поддерживается в `Swap`/`Push`, но `heap.Fix` нигде не вызывается. `durationEnv` в `internal/admin/config.go` не используется. Скомпилированные бинарники `main` (17 МБ) и `admin_panel` (17 МБ) лежат в рабочей директории.

**Смешение уровней в admin panel.** `cmd/admin_panel/main.go` собирает роутер, `internal/admin/*` содержит и store, и хендлеры, и парсинг конфига; шаблоны читаются по относительному пути `cmd/admin_panel/templates/...`, то есть бинарь работоспособен только из конкретного рабочего каталога (в Dockerfile это обходится копированием шаблонов в `/app/cmd/admin_panel/`). Правильнее — `embed.FS`.

## 5. Дефекты

Приоритеты: **P0** — ломает продукт прямо сейчас; **P1** — приводит к неверному результату при определённых условиях; **P2** — эксплуатационный риск; **P3** — качество кода.

### 5.1 P0 — критичные

**P0-1. `scripts/deploy.sh` без `TAG` откатит прод на 7 версий назад.**
`scripts/deploy.sh:6` — `export TAG="${TAG:-4.3.2}"`. В проде работает `4.3.9`. Запуск `./scripts/deploy.sh` без явного `TAG` выполнит `docker compose pull` + `up -d --force-recreate` и откатит все сервисы на `4.3.2`, потеряв при этом фиксы селекторов NeonSportz (`8ac3b0c`), таймаутов VPN (`b39eb59`, `fd68cba`) и `loadLogo` (`2226bbc`).

Тот же устаревший дефолт продублирован в:
- `docker-compose.yml` — `${TAG:-4.3.2}` в семи местах;
- `scripts/publish.sh:4`;
- `scripts/install.sh:6` — `DEFAULT_TAG="v4.3.2"`;
- `README.md` — во всех примерах команд.

Спасает только то, что в `.env` на Pi прописан `TAG=4.3.9`, и `env_file` его подхватывает. То есть катастрофы не происходит по случайности, а не по устройству.

**Фикс:** убрать дефолты версий из скриптов вообще (`TAG` обязателен, иначе `die`), в compose оставить `${TAG:?TAG is required}`.

### 5.2 P1 — неверный результат

> **Уточнено 2026-07-28 по фактическим данным.** Первоначальная формулировка была неточной, см. ниже.

**P1-1. Постсезонные посты выходят без списка матчей.**
`discord_kafka_week_formatter/internal/store/store.go:269`:
```go
stage := season == "regular"
```
`stage` — `BOOLEAN`. `regular` → `true`; `preseason` и `postseason` → `false`.

Разбор `MEGA_games.csv` показал, что `stageIndex` в реальных данных **всегда равен 1**, а плейофф идёт продолжением нумерации недель внутри той же стадии (season 0: weeks 0..22, где 18..22 — плейофф). Поэтому эффект дефекта не «подтянутся чужие пары команд», как предполагалось изначально, а **пустой список матчей**: в БД все записи лежат с `stage = true`, а для постсезона запрос ищет `false`. Плюс номер недели тоже не совпадёт — Discord сообщает «Post Season Week 1», тогда как игра лежит под `week_index = 18`.

**Решение (v5.0):** источника расписания плейоффа не существует — регулярка выгружается разово, плейофф не выгружается вовсе. Поэтому список матчей для постсезона не формируется намеренно, явным ранним возвратом с комментарием, а пост получает строку «Игра плейофф, расписание см. в игре». Хардкод `preseason && week == 4` уезжает в ту же явную логику.

**P1-2. ОТОЗВАН — вывод был ошибочным.**
Первоначально утверждалось, что `SELECT COALESCE(MAX(season_index), -1) FROM schedule_games` игнорирует `season_index` из payload и это надо исправить.

Проверка `parser.WeekUpdate` показала, что исправление технически невыполнимо:
```go
type WeekUpdate struct {
    Season string  // "regular" | "preseason" | "postseason" — ТИП сезона, не номер
    Week   int
    Title  string
}
```
Номера сезона в сообщении Discord нет вообще — только тип. Брать `season_index` неоткуда, и `MAX(season_index)` из расписания является единственным существующим источником. При разовой заливке текущего сезона он даёт корректный результат, а система дополнительно не зависит от того, видела ли она сообщение о смене сезона.

**Решение (v5.0):** поведение сохраняется, добавляются комментарий в коде, строка в документации и лог выбранного `season_index`.

**P1-2b. Потеря сообщений при длительном сбое Discord.** *(обнаружено при проработке v5.0)*
При недоступности Discord API `fetchAndParse` исчерпывает 10 попыток, затем `RecordAttempt` инкрементирует счётчик. После `PROCESS_MAX_ATTEMPTS=10` сообщение уезжает в `discord_message_failed` **безвозвратно** — хотя причина внешняя и временная. Получасовой сбой Discord выкидывает сообщения из конвейера навсегда.

**Фикс:** разделить ошибки на временные (таймаут, 5xx, 429, сетевые — попытка не засчитывается) и постоянные (404, не парсится — засчитывается).

**P1-2c. Сезон «Offseason» не распознаётся и молча пропадает.** *(обнаружено при реализации v5.0, на фикстурах с живого канала)*
`parser.parseWeek` знает три сезона: `Regular Season`, `Pre Season`, `Post Season`. Но в канале реально встречается заголовок **«MEGA has advanced to Offseason Week 1»** — четвёртый вариант, которого в списке нет.

Цепочка последствий прослежена по коду: нераспознанный сезон даёт `week == nil`, игр в таком сообщении тоже нет, поэтому `Ready == false` — ровно то же состояние, что и у сообщения, чьи embeds Discord ещё не успел заполнить. Дальше `fetchAndParse` по истечении `DISCORD_EMBED_WARMUP` возвращает `Skip: true`, и `handleMessage` вызывает `MarkProcessed`. В таблице появляется статус `processed` — **неотличимый от успешной обработки**, без ошибки, без записи в `failed`, только одна строка INFO «message skipped».

Ущерб невелик: в межсезонье игр нет, теряется лишь уведомление о самом переходе. Но диагностически это слепая зона — «пропущено намеренно» и «не распозналось» выглядят в базе одинаково.

**Фикс (не входит в v5.0):** добавить `Offseason` в словарь сезонов либо ввести отдельный статус для «распознано, но нечего публиковать», чтобы отличать его от успеха. Зафиксировано тестами `TestParseWeekOffseasonIsUnrecognisedAndNotReady` в `discord_kafka_processor/internal/parser/`.

**P1-3. Дубль поста в Telegram при отправке дольше минуты.**
`PROCESS_RETRY_INTERVAL=1m` используется одновременно как период тикера **и** как порог eligibility, причём в SQL стоит нестрогое `<=`:

```sql
-- telegram_week_sender/internal/store/store.go:111
WHERE status = 'new' AND (last_attempt_at IS NULL OR last_attempt_at <= $2)  -- $2 = now-1m
```

Сценарий: `consumeLoop` в момент T вызывает `TouchAttempt` (проставляет `last_attempt_at = T`), затем `SendWeekMessage`. HTTP-клиент Telegram имеет `Timeout: 2 * time.Minute` — то есть отправка законно может длиться дольше минуты. В момент T+60s `retryLoop` считает `cutoff = T`, условие `T <= T` истинно, сообщение подхватывается повторно и **отправляется в Telegram второй раз**.

У week-sender защиты нет вовсе: его `TouchAttempt` (строка 132) просто обновляет `last_attempt_at`, не переводя в `in_progress`, а `consumeLoop` не проверяет `in_progress`. Ошибка `TouchAttempt` в `processMessage` логируется как WARN и обработка продолжается.

У game-sender и game-image защита частичная — статус `in_progress` есть, но `ListPending` и `TouchAttempt` подхватывают `in_progress` по тому же граничному условию `last_attempt_at <= cutoff`, так что при зависании дольше минуты дубль возможен и там.

**Фикс:** развести период тикера и порог eligibility (например, порог = 3× интервала), заменить `<=` на `<`, привести `TouchAttempt` week-sender к варианту game-sender (`in_progress` + фильтр eligibility).

**P1-4. Fallback-карточку невозможно отличить от настоящего скриншота.**
`gochrome.Fetch` при неудаче скриншота возвращает `buildFallbackResult(...)` — заглушку 1600×900 из метаданных. В `types.Result` признака деградации нет, и в метаданные пишется `Fetcher: p.cfg.FetcherType` — то есть `"gochrome"` в обоих случаях. Отличить fallback от нормальной картинки можно только по размеру файла (~100 КБ против ~1,5 МБ) и по строчке WARN в логе.

Это ровно тот сценарий, где «сломался DOM после редизайна сайта» неделями выглядит как «всё работает»: конвейер зелёный, статусы `processed`, lag = 0, картинки отправляются.

**Фикс:** добавить в `types.Result` поле `Degraded bool` (или `Fetcher: "gochrome-fallback"`), писать его в Mongo/Postgres, выводить в дашборде и логировать на уровне ERROR.

**P1-5. `parseColor` ломается на цветах > 0xFFFFFF.**
`headless.go:590`:
```go
i, _ := strconv.ParseInt(dec, 10, 64)   // ошибка проигнорирована
hex := strconv.FormatInt(i, 16)
for len(hex) < 6 { hex = "0" + hex }    // дополняет, но не обрезает
r, _ := strconv.ParseInt(hex[0:2], 16, 64)
```
Для `i = 16777216` → `hex = "1000000"` (7 символов) → берутся байты `10`/`00`/`00` вместо ожидаемых. Пустая строка даёт чёрный цвет молча.

**P1-6. `headless` падает целиком при недоступности любого ассета.**
`buildRecapImage` последовательно грузит фон стадиона, два логотипа и логотип футера; любая ошибка возвращается наверх, вся генерация проваливается. В `gochrome` fallback предусмотрен, в `headless` — нет. При переключении фетчера на `headless` (см. 6.1) это станет актуальным.

**P1-7. Telegram Markdown без экранирования.**
`ParseMode = "Markdown"` при склейке `*%s*` и `[%s](%s)` из данных БД. Символы `_`, `*`, `[`, `` ` `` в `ShortName`, `Title` или нике игрока приведут к HTTP 400 от Telegram, десяти ретраям и переносу в `telegram_week_failed`.

### 5.3 P2 — эксплуатационные риски

**P2-1. Дашборд админки — полный скан всех статусных таблиц на каждый запрос.**
`internal/admin/store.go:197` — CTE с шестью `UNION ALL`, `GROUP BY message_id` по всему объединению, затем шесть `LEFT JOIN` и только в самом конце `LIMIT 50`. Сортировка `ORDER BY base.created_at DESC` идёт по вычисляемому агрегату, индексы неприменимы.

Сейчас данных ~1200 строк и это незаметно, но 4,52% CPU у простаивающей админки — уже отсюда. Рост линейный и неограниченный.

**Фикс:** ограничить `all_messages` окном (`WHERE created_at > now() - interval '30 days'`) и/или материализовать представление.

**P2-2. Нет ретеншена нигде.**
- Postgres: `*_status` растут вечно;
- MinIO: 818 МБ и +1,4 МБ на игру, без lifecycle-политики;

- Логи контейнеров: в `docker-compose.yml` нет секции `logging:`, значит `json-file` без `max-size`/`max-file` — рост без ограничений.

**P2-3. Health-check processor'а зависит от внешнего Discord API.**
`discord_kafka_processor/cmd/.../main.go:108` — `/health` возвращает 503, если `discordClient.Healthy()` ложно, а этот флаг обновляется раз в минуту вызовом `session.User("@me")`. Недоступность Discord API (или медленный VPN) → контейнер `unhealthy` → autoheal его перезапускает. Внешний сбой конвертируется в локальный рестарт, который ничего не чинит. Ту же природу имеет уже применённый фикс `cdce5e7` (увеличение healthcheck timeout).

**P2-4. `kafkaPing` проверяет только TCP-коннект.**
Четыре сервиса считают Kafka здоровой по факту успешного `net.Dial` к `brokers[0]`. Брокер, принимающий соединения но не отдающий метаданные, пройдёт проверку.

**P2-5. Нет `.dockerignore`.**
В контекст сборки уезжают `main` (17 МБ), `admin_panel` (17 МБ), `MEGA_games.csv`, `.git`. Плюс все сервисные Dockerfile'ы явно делают `COPY .git ./.git` ради `git describe` — при том что CI и так передаёт `VERSION`/`COMMIT`/`BUILD_DATE` через `build-args`, так что копирование `.git` в проде избыточно.

**P2-6. Миграция в горячем пути старта.**
`week_formatter/store.go:111` — `EnsureSchema` при каждом запуске выполняет `DELETE FROM schedule_games a USING schedule_games b ...` (дедупликация). Разовая миграция, выполняемая на каждом рестарте.

**P2-7. `MINIO_PUBLIC_URL=http://localhost:9000`.**
В Kafka-события, Mongo и Postgres пишется URL с `localhost`, который валиден только на самом хосте. Админка чинит это на лету (`resolveImageURL`), но в данных остаётся неверная ссылка.

**P2-8. Listener работает от root.**
`docker-compose.yml:103` — `user: "${DISCORD_LISTENER_USER:-0:0}"`, чтобы писать `last_message_id` в том. Остальные шесть сервисов — non-root. Решается `chown` тома при инициализации.

### 5.4 P3 — качество

- **P3-1.** `buffered_writer.go:80,118,141,145` — поле `processing` мертво: устанавливается и сбрасывается внутри одной ветки `select`, поэтому в момент чтения из `w.incoming` всегда пустое. Проверка `if id == processing { continue }` не срабатывает никогда.

- **P3-4.** `week_formatter/store.go:256` — `if season == "preseason" && week == 4 { return nil, nil }`: бизнес-правило хардкодом без комментария.
- **P3-5.** `formatter.go:53` — дедлайн `time.Now().Add(40 * time.Hour)` считается в момент форматирования, а не отправки; «40 часов» не конфигурируется.
- **P3-6.** `telegram-bot-api v4.6.4+incompatible` — архивная ветка библиотеки, актуальна `v5`.
- **P3-7.** Расхождение версий Go: корневой `go.mod` — `go 1.24.0`, шесть сервисных — `go 1.25.5`, Dockerfile'ы — `golang:1.25.5-alpine`, AGENTS.md утверждает «Go 1.24».

- **P3-9.** `layout.html` содержит кнопку «Log out» с `href="#"` — след незаконченной авторизации.
- **P3-10.** Админка тянет CSS/JS с внешних CDN (`jsdelivr`, `unpkg`) — без сети админка выглядит сломанной.

Диск 72% → ~48%. Дальше — в cron еженедельно.

### 6.1 Kafka без Zookeeper (KRaft) — −90 МБ

`confluentinc/cp-kafka:7.6.1` поддерживает KRaft. Убирает целый контейнер и JVM. Изменения кода — нулевые, конфигурация compose переписывается на `KAFKA_PROCESS_ROLES=broker,controller`. ### 6.2 Или: Kafka → Redpanda — −200 МБ

`redpandadata/redpanda` — Kafka API-совместимый брокер на C++ без JVM и без Zookeeper, ~150–200 МБ вместо 480 МБ. Код (`segmentio/kafka-go`) не меняется вообще, меняется только образ и команда запуска. Для нагрузки в 600 сообщений это функционально эквивалентная замена.

### 6.3 Убрать MongoDB — −66 МБ, −1 контейнер

`discord_kafka_game_image` пишет **одни и те же данные в оба хранилища**. Сравнение:

| Данные | Mongo (`game_images`) | Postgres (`game_image_status`) |
|---|---|---|
| статус, attempts, last_error | ✅ | ✅ |
| payload (game_id, game_url) | ✅ | ✅ (JSONB) |
| метаданные картинки | ✅ | ✅ (JSONB `image`) |
| таймстемпы | ✅ | ✅ |
| failed-коллекция/таблица | ✅ | ✅ |

`processor.go` буквально дублирует каждый вызов: `touchAttempt`, `recordAttempt`, `markProcessed`, `moveToFailed`, `updateMetadata` — все обращаются сначала к `pg`, потом к `store` (Mongo). Ни одного поля, которое есть только в Mongo, нет. Админка читает исключительно Postgres.

Удаление: убрать `internal/store/store.go`, снять дублирующие вызовы в `processor.go`, убрать `mongo` из compose и `MONGO_*` из env. Плюс исчезает Mongo-проверка из `/health` и `waitForMongo` из старта.

> **Уточнение 2026-07-28.** Это не «выключить контейнер»: в `pgstore` отсутствует метод `ListPending`, он есть только в Mongo-сторе, и именно его использует `reprocessPending` для добора недоделанной работы при старте. Требуется дописать SQL-аналог (почти дословно копируется из четырёх других сервисов) и переключить `reprocessPending` на него. Данные при этом не мигрируют: сверка показала 600/600 записей с заполненным `image_url` в обоих хранилищах.

### 6.5 Разредить health-check'и — экономия CPU

Сейчас 13 контейнеров опрашиваются каждые 5–10 секунд, плюс autoheal сканирует Docker API каждые 5 секунд. Самые дорогие:

- `postgres`: `pg_isready` каждые **5 с** — форк процесса;
- `mongo`: запуск shell-клиента каждые **5 с** (после 6.3 исчезнет);
- шесть Go-сервисов: `/health` каждые 10 с, причём каждый вызов делает `Ping` в Postgres/MinIO + TCP к Kafka.

Для системы, которая работает раз в неделю, `interval: 30s` более чем достаточно. Это ~4-кратное снижение фонового CPU от healthcheck'ов.

### 6.6 Кэш шрифтов — дешёвый выигрыш CPU

`headless.loadFont(size)` вызывает `truetype.Parse(goregular.TTF)` при **каждом** вызове, а вызывается он ~15 раз на одну картинку. То же в `gochrome.scoreFont`. Парсинг TTF на ARM — не бесплатно.

```go
var ttfOnce sync.Once
var parsedTTF *truetype.Font

func loadFont(size float64) font.Face {
    ttfOnce.Do(func() { parsedTTF, _ = truetype.Parse(goregular.TTF) })
    return truetype.NewFace(parsedTTF, &truetype.Options{Size: size, DPI: 72, Hinting: font.HintingFull})
}
```

### 6.7 Переиспользование Chrome

`screenshotRecapWrapper` создаёт новый `chromedp.NewExecAllocator` на **каждую игру** — то есть полный запуск процесса Chromium. При пачке из 12 игр это 12 холодных стартов (~2–3 с каждый) и 12 пиков памяти по 150–250 МБ.

Держать один allocator на уровне `Client` и создавать на игру только новую вкладку (`chromedp.NewContext(c.allocCtx)`) сокращает и время, и пик памяти. Риск — накопление утечек в долгоживущем Chrome; митигируется пересозданием allocator'а каждые N игр (например, 20) или по таймеру.

Выигрыш во времени: ~25–30 с на игру сейчас, из них 2–3 с — старт браузера. Экономия ~10%. Основное время уходит на сеть и ожидание ассетов.

### 6.8 Радикально: `headless` вместо `gochrome` — −676 МБ образа

Это самая крупная разовая экономия, но она **требует вашего решения о качестве картинки**.

| | `gochrome` (сейчас) | `headless` |
|---|---|---|
| Размер образа | **701 МБ** | ~25 МБ |
| RAM в пике | +150–250 МБ (Chromium) | +10–20 МБ |
| Время на игру | 25–30 с | 1–2 с (только HTTP + отрисовка) |
| Зависимость от вёрстки NeonSportz | **высокая** (редизайн ломает всё) | нет (только JSON API) |
| Внешний вид | пиксель-в-пиксель как на сайте | своя вёрстка на `gg` |

`headless` полностью снимает целый класс инцидентов — тот самый, что породил коммиты `8ac3b0c` (селекторы после редизайна), `fd68cba` и `b39eb59` (таймауты). Он зависит только от JSON API, который стабильнее DOM.

Цена — картинка выглядит иначе: это самостоятельная отрисовка (фон стадиона, две строки команд с логотипами и счётом, блок статистики 4×2, футер), а не копия сайта.

**Рекомендация:** сгенерировать одну и ту же игру обоими фетчерами и сравнить визуально. Если `headless`-вариант приемлем — это минус 676 МБ образа, минус Chromium из памяти, минус 20× по времени обработки и минус самый хрупкий компонент системы. Перед переключением нужно закрыть P1-6 (fallback при недоступности ассетов).

### 6.9 Стратегически: убрать брокер совсем — −480 МБ

Как показано в 2.4, Kafka здесь не источник истины: коммит offset происходит сразу после записи в Postgres, а восстановление идёт из `reprocessPending`. Каждый сервис уже имеет статусную таблицу с идемпотентными вставками. Kafka выполняет ровно одну функцию — «разбудить следующий сервис».

Postgres уже развёрнут и потребляет 29 МБ. Замена на очередь в нём:

```sql
SELECT message_id FROM discord_message_status
 WHERE status = 'new'
 ORDER BY created_at
 FOR UPDATE SKIP LOCKED
 LIMIT 1;
```

`FOR UPDATE SKIP LOCKED` даёт корректную конкурентную выборку без брокера. Пробуждение — либо `LISTEN/NOTIFY`, либо polling раз в 5–10 секунд (для батча раз в неделю этого с запасом достаточно).

Выигрыш: −480 МБ RAM, −2 контейнера, минус вся Kafka-обвязка (producers, readers, `kafkaPing`, `kafka-init`, топики, consumer-группы) — это ~500 строк кода и целый слой эксплуатации.

Риск высокий: это переписывание транспорта во всех шести сервисах. Но объём меньше, чем кажется — межсервисные payload'ы уже сериализуются в JSON и уже лежат в Postgres.

### 6.10 Стратегически: слияние сервисов

Семь Go-контейнеров = 68,5 МБ RAM, семь health-серверов, семь пулов pgx (10 активных соединений к Postgres), семь копий одинакового бутстрапа. Разделение оправдано при независимом масштабировании — здесь его нет и не будет: всё работает строго последовательно на одном хосте.

Умеренный вариант — слияние по доменам: `week` (formatter + sender) и `game` (image + sender), плюс listener и processor. 7 → 4 контейнера, −20 МБ, и исчезают два межсервисных Kafka-хопа.

Радикальный — один бинарь с горутинами вместо контейнеров: −50 МБ, минус вся сетевая сериализация между стадиями. В сочетании с 6.9 это сводит весь стек к трём контейнерам: `app` + `postgres` + `minio` (~150 МБ вместо 742 МБ).
