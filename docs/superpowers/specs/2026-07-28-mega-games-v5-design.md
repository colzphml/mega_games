# MEGA Games Bot v5.0 — дизайн

**Дата:** 2026-07-28
**Основание:** `AUDIT.md` (полный аудит от 2026-07-28)
**Ветка реализации:** `release-5.0` (от `release-4.0`)
**Целевой релиз:** `v5.0.0`, одним выпуском

---

## 1. Контекст и цели

Система работает корректно: 13 контейнеров healthy, lag = 0, за сутки одна запись WARN, `go vet` чист. Проблема не в багах, а в несоответствии масштаба инфраструктуры масштабу задачи.

Фактическая нагрузка — батч раз в неделю: приходит ~12 игр, обрабатываются за 5–6 минут, дальше простой. Под это развёрнуты Kafka + Zookeeper (480 МБ = 65% стека), MongoDB, полностью дублирующая Postgres, и 7 отдельных Go-контейнеров.

**Цели v5.0:**

1. Снизить потребление RAM примерно вдвое без потери функциональности.
2. Закрыть дефекты P0/P1/P2 из аудита.
3. Сделать код тестируемым и покрыть его так, чтобы будущие изменения проверялись автоматически.
4. Привести эксплуатацию в порядок: ретеншен, лимиты, безопасность, документация.

**Явно не цели:** переход на монолит, замена брокера на очередь в Postgres, смена генератора картинок. Это кандидаты в v6.0, решение отложено сознательно.

## 2. Принятые решения

| # | Блок | Решение | Обоснование |
|---|---|---|---|
| 1 | Масштаб | Умеренное упрощение, архитектура узнаваема | Максимальный выигрыш при низком риске |
| 2 | Транспорт | Kafka + Zookeeper → **Redpanda** | Kafka API-совместим, код Go не меняется, −280 МБ |
| 3 | MongoDB | **Удалить** | Полный дубль `game_image_status`; сверено 600/600 |
| 4 | MinIO | **Оставить** + прямые ссылки в админке | Нужен архив картинок и превью в дашборде |
| 5 | Границы сервисов | **7 сервисов остаются** | Слияние дало бы ~20 МБ (3%) при среднем риске |
| 6 | Генерация картинок | **gochrome остаётся** + оптимизации | Качество важнее ресурсов; headless — запасной |
| 7 | Железо | swappiness=10, лимиты памяти, очистка диска | zram отложен до замера после v5.0 |
| 8 | Безопасность | Закрыть порты, сменить пароли, basic-auth админке | Открыты БД с дефолтными паролями и админка с DELETE |
| 9 | Тесты | **Полная пирамида** + DI-рефакторинг | Требование: будущие изменения тестируются корректно |
| 10 | Выкатка | Один релиз `v5.0.0`, вся история сохраняется | Жёсткое требование заказчика |

## 3. Архитектура v5.0

Поток данных, границы сервисов и модель надёжности через статусные таблицы **не меняются**. Postgres остаётся источником истины, Redpanda — транспортом «разбуди следующего».

### Стек

| Компонент | Было | Стало | Δ RAM |
|---|---|---|---|
| kafka + zookeeper | 480 МБ, 2 контейнера | redpanda, 1 контейнер | −280 МБ |
| mongo | 66 МБ | удалён | −66 МБ |
| minio | 98 МБ | 98 МБ + lifecycle | 0 |
| postgres | 29 МБ | 29 МБ | 0 |
| 7 Go-сервисов | 68 МБ | 68 МБ | 0 |
| **Итого** | **~742 МБ** | **~395 МБ** | **−47%** |

Контейнеров: 13 → 11. Диск: −13,6 ГБ образов немедленно.

**Оценка Redpanda в 200 МБ не является замером.** Это ориентир по документации. Обязательные флаги под Pi: `--overprovisioned --smp 1 --memory 512M --reserve-memory 0M`. Если после выкатки замер окажется хуже Kafka — откат на `confluentinc/cp-kafka` в режиме KRaft (гарантированные −90 МБ за счёт удаления Zookeeper).

## 4. Изменения в коде

### 4.1 Общий модуль

Появляется корневой пакет, куда переезжает продублированный по шесть раз код (~800 строк):

```
internal/common/
  config/   requiredEnv, optionalEnv, durationEnv, intEnv, splitAndTrim
  health/   startHealthServer, liveness/readiness, waitFor*
  queue/    единая логика eligibility и переходов статусов
  retry/    sleepWithContext, backoff, классификация ошибок
```

Главная ценность не в экономии строк, а в невозможности расхождения реализаций — именно расхождение породило P1-3.

### 4.2 Инъекция зависимостей

Предпосылка к тестируемости. Сейчас зависимости создаются внутри функций, подменить их нечем:

```go
// было
func fetchJSON(ctx context.Context, url string, timeout time.Duration) (Recap, error) {
    client := &http.Client{Timeout: timeout}
}
func New(cfg config.Config, store *store.Store, discordClient *discord.Client, ...)
```

```go
// станет
type MessageFetcher interface {
    FetchMessage(ctx context.Context, id string) (*discordgo.Message, error)
}
type Sender interface {
    Send(ctx context.Context, msg Message) error
}
func New(cfg config.Config, deps Deps)  // Deps содержит интерфейсы
```

Затрагивает шесть `main.go` и все процессоры. Поведение не меняется, меняется структура.

### 4.3 Дефекты

**P0-1. Устаревший дефолт `TAG`.** В `deploy.sh`, `publish.sh`, `install.sh` и `docker-compose.yml` стоит `4.3.2` при `4.3.9` в проде. Запуск `./scripts/deploy.sh` без явного `TAG` откатил бы прод на 7 версий, потеряв фиксы селекторов NeonSportz и таймаутов VPN. Дефолты убираются полностью: переменная обязательна, без неё скрипт падает с внятной ошибкой.

**P1-3. Дубли постов в Telegram.** Причина: `PROCESS_RETRY_INTERVAL` служит одновременно периодом тикера и порогом eligibility, причём в SQL стоит нестрогое `<=`. Отправка, длящаяся ≥ 60 с (а HTTP-таймаут Telegram — 2 минуты), подхватывается повторно.

Исправление в `internal/common/queue`: порог eligibility = 3× интервала тикера, `<=` → `<`, статус `in_progress` работает одинаково во всех пяти сервисах. У `telegram-week-sender` появляется отсутствующая сейчас защита `in_progress`.

**Новое (не было в аудите). Потеря сообщений при сбое Discord.** При недоступности Discord API `RecordAttempt` инкрементирует счётчик, и после 10 попыток сообщение уезжает в `discord_message_failed` безвозвратно — хотя причина внешняя и временная. Получасовой сбой Discord выкидывает сообщения из конвейера навсегда.

Исправление: классификация ошибок.
- **временные** (таймаут, 5xx, 429, сетевые) — попытка не засчитывается, сообщение ждёт восстановления;
- **постоянные** (404, сообщение не парсится) — попытка засчитывается, после лимита уходит в `failed`.

**P2-3. Health-check зависит от внешнего Discord.** Сейчас недоступность Discord делает контейнер unhealthy, и autoheal его перезапускает — рестарт ничего не чинит, получается луп.

Исправление: `/health` (liveness) проверяет только сам сервис — Postgres, брокер. `/ready` (readiness) дополнительно учитывает Discord. Autoheal смотрит только на `/health`. Недоступность Discord видна в логах и в дашборде, но рестарта не вызывает.

**P1-1. Постсезон.** Уточнение по фактическим данным: в `MEGA_games.csv` `stageIndex` всегда `1`, плейофф идёт продолжением нумерации недель (season 0: weeks 0..22). Реальный эффект дефекта — пустой список матчей в посте, а не неверные пары команд.

Решение: **источника расписания плейоффа не существует** — регулярка выгружается разово, плейофф не выгружается вовсе. Поэтому для postseason список матчей не формируется намеренно, с явным ранним возвратом и комментарием. Хардкод `preseason && week == 4` уезжает в ту же явную логику.

Формат поста для плейоффа:

```
*MEGA has advanced to Post Season Week 1*

Игра плейофф, расписание см. в игре

_❗️Пожалуйста, договоритесь прямо сейчас о матче
во избежание затяжек шага.

До 30 Jul 2026 10:20 просьба указать анонс
матча реплаем к этому посту_
```

**P1-2. ОТОЗВАН как ошибочный вывод аудита.** Утверждение «`season_index` надо брать из payload» технически невыполнимо: `parser.WeekUpdate` содержит только *тип* сезона (`regular`/`preseason`/`postseason`), номера сезона в сообщении Discord нет вообще. `MAX(season_index)` из расписания — единственный существующий источник, и при разовой заливке текущего сезона он даёт правильный ответ. Дополнительный плюс: система не зависит от того, видела ли она сообщение о смене сезона.

В v5.0 поведение сохраняется, добавляются комментарий в коде, строка в документации и лог выбранного `season_index`.

**P1-4. Fallback-карточки неотличимы.** При падении скриншота `gochrome` возвращает заглушку ~100 КБ, но в метаданные пишется `fetcher: "gochrome"` — как и при успехе. Отличить можно только по размеру файла. Именно так сломанный после редизайна DOM неделями выглядит как «всё зелёное».

Исправление: `types.Result` получает признак деградации, в метаданные пишется `fetcher: "gochrome-fallback"`, дашборд подсвечивает такие записи, лог пишется на уровне ERROR.

**P1-7. Экранирование Markdown.** `ParseMode = "Markdown"` со склейкой `*%s*` и `[%s](%s)` из данных БД. Символы `_ * [ ` ` в названии команды или нике игрока дадут HTTP 400 и перенос в `failed`. Добавляется экранирование с тестом на спецсимволы.

**P2-1. Запрос дашборда.** Полный скан шести таблиц с `UNION ALL` и `GROUP BY`, `LIMIT` применяется в конце — отсюда 4,5% CPU у простаивающей админки. Ограничивается окном 30 дней. История при этом сохраняется полностью, ограничивается только отображение.

**Прочее.** `ListPending` дописывается в `pgstore` (нужен для удаления Mongo — сейчас метод есть только в Mongo-сторе). `parseColor` чинится (ломается на цветах > 0xFFFFFF). Удаляется мёртвый код: пакет `selenium` целиком, `retryItem.index`, неиспользуемые функции. Версии Go выравниваются на 1.25.5. `MINIO_PUBLIC_URL` перестаёт быть `localhost`. Дедлайн 40 часов выносится в конфигурацию.

### 4.4 Оптимизация gochrome

- Chrome переиспользуется между играми в пределах пачки; allocator пересоздаётся каждые 20 игр или при первой же ошибке запуска вкладки — во избежание накопления утечек в долгоживущем процессе. Значение 20 выбрано с запасом относительно типичной пачки в ~12 игр, то есть в штатном режиме пересоздание не происходит вовсе.
- Шрифты парсятся один раз через `sync.Once` вместо ~15 раз на картинку.
- `headless` остаётся рабочим запасным вариантом; для него закрывается P1-6 (падение всей генерации при недоступности любого ассета).

## 5. Тестирование

Пирамида в четыре слоя. Требование — покрыть так, чтобы будущие изменения проверялись автоматически.

| Слой | Что покрывает | Инструмент |
|---|---|---|
| unit (~20) | парсер Discord, форматтер поста, экранирование, маппинг недель, `parseColor`, `JSONInt`, `ObjectKey` | чистый `go test`, без инфраструктуры |
| component (~25) | логика процессоров целиком, ретраи и классификация ошибок, отправка в Telegram | фейки через интерфейсы + `httptest` |
| integration (~20) | статусы и eligibility, идемпотентность, транзакции, publish/consume, upload/download | testcontainers |
| smoke (~2) | реальный Chrome на живой странице | по флагу, вне обычного прогона |

**Способ по каждой внешней зависимости:**

- **Postgres** — testcontainers, реальная БД. Логика статусов — это SQL; мок проверил бы фантазию, а не поведение `ON CONFLICT` и границ сравнения. Здесь сидит P1-3.
- **Telegram** — `httptest` + подмена `bot.APIEndpoint`. Не мок, а настоящий HTTP: проверяем, что реально уходит в `sendMessage` — экранирование, `parse_mode`, размер фото.
- **Discord** — интерфейс `MessageFetcher` + фейк, отдающий записанные JSON'ы реальных сообщений. Фикстуры снимаются утилитой `discord_tools/message-dump`.
- **NeonSportz API** — `httptest` + инжектированный `*http.Client`, ответы из `testdata/`. Покрывает `JSONInt`, обработку 404/429/таймаутов.
- **Chrome** — не мокается. В тестах конвейера подставляется фейковый `middle.Fetcher` (интерфейс уже существует).
- **MinIO** — testcontainers, реальный upload/download и генерация ключей.
- **Redpanda** — testcontainers (стартует ~3 с против ~30 с у Kafka).

Тесты добавляются в CI-workflow; для testcontainers требуется Docker в CI (в GitHub Actions доступен из коробки).

## 6. Инфраструктура и безопасность

**Лимиты памяти.** Сейчас `mem_limit` есть только у Kafka и Zookeeper, и только в **незакоммиченном** `docker-compose.override.yml` на живом хосте — он потерялся бы при любой переустановке. Лимиты переезжают в git и распространяются на все контейнеры: `game-image` 512 МБ (Chromium), `postgres` 256 МБ, `minio` 192 МБ, остальные 64 МБ. Смысл: OOM одного контейнера перестаёт быть смертью хоста.

**Логи.** Добавляется `logging` с `max-size: 10m, max-file: 3` — сейчас драйвер `json-file` работает без ограничений.

**Порты.** Наружу остаются только админка (8002, с basic-auth) и MinIO API (9000, для прямых ссылок на картинки). Postgres, брокер и консоль MinIO уходят внутрь сети compose. Пароли `megagames/megagames` меняются на всех хранилищах.

**Хост.** `swappiness=10` через `/etc/sysctl.d/`. Разовая очистка 13,6 ГБ образов плюс еженедельный `image prune` в cron. Health-check'и разрежаются с 5–10 с до 30 с.

**Известные риски без работ в v5.0:** тепловой троттлинг (`throttled=0xe0000` подтверждает, что он уже случался; 75,9 °C в покое при пороге 80 °C) и размещение всех данных на SD-карте. Требуют физического вмешательства, вынесены за рамки.

## 7. Миграция и сохранность истории

**Жёсткое требование: вся история сохраняется.** Фиксируется проверяемыми числами, снимаемыми до миграции и сверяемыми после.

| Что | Эталон |
|---|---|
| `discord_message_status` | 572 processed |
| `game_image_status` | 600, из них 600 с `image_url` |
| `telegram_game_status` | 600 processed |
| `week_message_status` / `telegram_week_status` | 49 / 49 |
| MinIO `game-images` | 818 МБ, 600 объектов |

**Порядок:**

1. `pg_dump` всей базы, снимок тома MinIO, копии `.env` и compose.
2. Остановить `listener`, дождаться `lag = 0` по всем группам.
3. Погасить стек, поднять новый compose с Redpanda. Топики создаются пустыми — безопасно, поскольку незавершённая работа лежит в Postgres и добирается через `reprocessPending` при старте.
4. Mongo удаляется из compose, **том остаётся на диске** как страховка.
5. Сверка эталонных чисел. Расхождение хоть на одну строку — откат.

Схема Postgres не меняется ни одной миграцией. MinIO не трогается. Lifecycle-политика на автоудаление **в этом релизе не активируется** — настраивается позже отдельным решением, чтобы гарантированно ничего не потерять.

Единственная точка риска — переход на Redpanda: consumer-группы и offset'ы не переносятся. Защита — миграция только при `lag = 0` с остановленным listener.

## 8. Релиз и откат

Ветка `release-5.0` от `release-4.0`. Один релиз `v5.0.0`: GitHub Actions публикует multi-arch образы в GHCR, на Pi выполняется только `pull` + `up`.

`docker-compose.override.yml` фиксируется в git. README и AGENTS.md приводятся в соответствие с фактическим состоянием: версии Go, дефолтный фетчер, отсутствие Mongo, актуальные версии в примерах команд.

**Откат:** вернуть `TAG=4.3.9` и прежний `docker-compose.yml`, поднять Kafka/Zookeeper/Mongo. Тома Postgres, MinIO и Mongo целы, поэтому откат занимает минуты и не теряет данных.

## 9. Что сознательно не делаем

| Отложено | Причина |
|---|---|
| Монолит, слияние сервисов | Выигрыш ~20 МБ (3%) при среднем риске |
| Postgres-очередь вместо брокера | Переписывание транспорта в шести сервисах |
| Переход на `headless` | Качество картинки важнее ресурсов |
| zram | Сейчас решает несуществующую проблему: `available = 2511 МБ`, дефицита нет. После освобождения ~350 МБ своп, вероятно, перестанет использоваться. Условие возврата: если после v5.0 своп всё ещё расходуется |
| Охлаждение, перенос с SD | Требует физического вмешательства |
| Активация lifecycle MinIO | Отложена ради гарантии сохранности истории |

## 10. Критерии приёмки

1. Все эталонные числа из раздела 7 совпадают до и после миграции.
2. `docker stats` показывает суммарное потребление стека ≤ 450 МБ.
3. Все контейнеры `healthy`, lag = 0 по всем группам.
4. Полный цикл проходит end-to-end: сообщение в Discord → пост и картинка в Telegram.
5. `go test ./...` зелёный во всех модулях; тесты выполняются в CI.
6. Наружу открыты только 8002 и 9000; админка требует аутентификации.
7. `./scripts/deploy.sh` без `TAG` завершается ошибкой, а не откатом прода.
8. Дефолтные пароли `megagames/megagames` отсутствуют.
9. Fallback-карточка отличима от настоящего скриншота в дашборде и логах.
10. Сбой Discord на 30 минут не приводит к потере сообщений.

## 11. Поправки к AUDIT.md

По итогам проработки в аудит вносятся исправления:

- **P1-1** переформулирован: реальный эффект — пустой список матчей, а не неверные пары команд (`stageIndex` в данных всегда `1`).
- **P1-2** отозван как ошибочный: номера сезона нет в сообщении Discord, `MAX(season_index)` корректен.
- **Добавлен новый дефект:** потеря сообщений при длительном сбое Discord из-за отсутствия классификации ошибок.
- **Уточнено:** удаление Mongo требует реализации `ListPending` в `pgstore`, это не «выключить контейнер».
